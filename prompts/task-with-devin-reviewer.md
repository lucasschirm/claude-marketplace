---
description: Implement a GitHub issue end-to-end, get the PR reviewed by Devin, and drive it to green
argument-hint: <issue-title-or-number> [base-branch]
---
Start working on the issue `$1` (if a title is given, resolve it to the issue number with `gh` first).

- Base your branch on `${2:-dev}`.
- Before starting work, associate the branch with the issue: name the branch so it contains the issue number (e.g. `...-<issue-number>`), and reference `#<issue-number>` in the first commit message — so GitHub links the branch's commits and the resulting PR to the issue from the very start.
- Read the full issue body and write a complete implementation plan before writing any code. Don't ask for approval first — just plan, then proceed.
- Before committing, review every changed file: check for existing references to each file elsewhere in the codebase, and look for documentation that is now stale.
- Open the PR against `${2:-dev}` as the base branch, and, as part of creating it, explicitly use `gh` to associate the PR with the issue: set the PR body (via `gh pr create --body`, or `gh pr edit <pr> --body` right after creation) to include a closing reference to `#<issue-number>`, then verify the association with `gh pr view <pr> --json closingIssuesReferences`.
- After the PR is created, have Devin review it with the `devin_delegate` tool — the `delegate-to-devin` skill shipped with this package has the full workflow, and this is its "implementation review" class. Use `model: "swe-2-max"`, `mode: "dangerous"`, and no worktree: a read-only review runs unattended, and the no-write instruction below is what keeps it read-only. Devin starts with no memory of this conversation, so the task must be self-contained. For every review round, use exactly this task text — no further guidance, instruction, or background information: "Review the PR #<pr-number>. Fetch the PR branch and review the full diff against the base branch for correctness, security, error handling, and the repo's conventions. Do not modify any files, push, or close the PR. Report findings classified as Blocker / Major / Minor with file:line references, and state what you verified. A negative result (no findings) is a valid deliverable. Do not invent findings."
- `devin_delegate` returns immediately and the review runs in the background. Do not poll `devin_status` in a loop — a follow-up message arrives when the session finishes. Read the result with `devin_status` (`session_id`, `complete: true` for the full transcript). Answer any permission request the session raises with `devin_permission`, and if the session fails or is interrupted, resume it with `devin_restart` rather than re-delegating from scratch.
- Address findings, resolve the review conversations Devin opened on the PR as you address each finding (the `pr_task_*` tools track them), then request another Devin review using that same exact task text if any Blocker or Major findings were raised in the last review round. Repeat only while Blocker or Major findings remain.
- Once Devin approves, monitor CI and fix any failures until it's green. Do not run another Devin review after approval — a new review is only ever triggered by a previous round that raised Blocker or Major findings, never by a push on its own.
- When CI is green, add the "Ready to review" label to the PR. The task is then done.
